# Project audit & review

*A review of the SPORE reference implementation: what's here, how good it is, and
what each target platform needs. Written against the code, not the intentions.*

## Verdict

The repository is a **complete, tested reference implementation of the SPORE v1
spec** (§1–§10 plus the Page-2 bindings), ~4,950 lines of Rust with **32 passing
tests and zero warnings**, plus a C ABI with autogenerated Python/Go/JS wrappers
(each smoke-tested). The architecture holds: one medium-independent router, and
everything else — files, sessions, crypto, anonymity, congestion, bridges — is
additive and, where it belongs, generic. It is suitable as a spec-faithful
reference and a starting point for real deployments. It is **not** yet a
hardened, multi-platform product; the gaps are known and listed below.

## Code quality

<details>
<summary>Strengths, and the honest weak spots</summary>

**Strengths.** Small, layered, well-commented; the transport/router boundary is
crisp; bridges share one address resolver and (now) one datagram driver so a new
medium is a thin `recv`/`send` shim; no `unsafe` outside the FFI; deterministic
tests cover every layer end-to-end.

**Weak spots worth knowing.**
- `src/lib.rs` is ~3,100 lines — the router/crypto/app layers could be split into
  files like `bridge/` already is. Cosmetic, not correctness.
- The Meshtastic codec is a **template**: protobuf field numbers, the multicast
  group/port, and channel encryption must be checked against real firmware (called
  out in the module). Not hardware-verified here.
- Mix mode ships the crypto + batching; the **timing policy** (Poisson delay,
  decoy traffic) and **KEYROT** are documented conventions, not code.
- The reliable stream is Go-Back-N with a fixed window — correct, not tuned.
- Store eviction can drop in-progress file chunks under memory pressure (no
  pinning). Fine for a reference; note for production.
</details>

## Security review

<details>
<summary>What's sound, and what to check before trusting it</summary>

- **Cryptographic identity is self-authenticating** (address = hash of the
  Ed25519 key); path learning and `Neighbors` bind only from *signed* frames, so
  an attacker can't claim someone else's address without their key. Interception
  of a directed unicast heals via flood-fallback (§5.6), and confidentiality is
  end-to-end, so it degrades to ARP-spoofing-grade nuisance, not compromise.
- **Forward secrecy** comes from prekey rotation and the Double Ratchet; replays
  are rejected (envelope dedup, ratchet skip-window, session replay window).
- **`src/ffi.rs` is `unsafe` by nature** (a C ABI trusts caller pointers/lengths).
  The generated wrappers uphold the contract, but any hand-written FFI caller must
  too. This is the main surface a security pass should focus on.
- **Not yet done:** per-source/topic quotas (§10) to blunt flooding abuse; a
  global-observer defence for mix mode (needs flowing decoys); constant-time
  review of the hand-rolled Base32/protobuf (low risk — not key-dependent).
- No unsafe deps beyond the vetted RustCrypto/dalek stack; deps are pinned.
</details>

## Portability — the platform daemon

A **single config-driven daemon** (`src/main.rs`, `cargo run -- node.yaml`) runs
any set of bridges on one shared node. Because it's plain `std` (threads +
sockets + fs), the same binary targets every desktop and mobile OS; the browser
and microcontrollers need a thin platform layer over the *same* core.

<details>
<summary>Deep dive: status per target, and what each still needs</summary>

| Target | Core | Daemon | What's needed |
|---|---|---|---|
| **Linux** | ✅ | ✅ tested here | — |
| **macOS** | ✅ | ✅ (std) | build + CI on macOS; only Linux is exercised here |
| **Windows** | ✅ | ✅ (std) | build + CI; sockets/threads are `std`, so it should just compile |
| **Android** | ✅ | ✅ (std) | cross-compile with the NDK; wrap the daemon in a foreground service; add WiFi-Direct/BLE bridges |
| **Web / wasm** | ✅ | ✅ *(node + hub + transports)* | ships in `web/`: `wasm32` build with a single import (getrandom `custom` backend, no wasm-bindgen), a node ABI (`src/wasm.rs`), and a JS `Hub` that relays across transports. Loopback and a real WebSocket relay are tested end-to-end in Node; WebRTC and Nostr transports are written |
| **ESP32** | ◑ | ▢ | build under `esp-idf` (which provides `std`); implement one `DatagramTransport` for ESP-NOW/Wi-Fi. The generic driver + `Neighbors` are reused unchanged |

**Web transports** (all thin JS shims: a `send(bytes)`/`receive(bytes)` pair over
the browser's own API, dispatched by the JS `Hub`). Shipped and tested: WebSocket
(browser + Node), loopback. Shipped, browser-only: WebRTC DataChannel, Nostr relays
(kind-30078). Still to wrap, same shape: WebTransport (QUIC), Web Serial/USB (drive
a TNC), Web Bluetooth (GATT), ultrasonic (ggwave), QR camera. See `web/README.md`.

**The key point:** the medium-independent work — router, `Neighbors<U>`,
fragmentation, the datagram driver — is all in the portable lib. Every remaining
platform/transport is a `recv`/`send` shim, exactly as the ESP32 and browser rows
above describe.
</details>

## Recommendations (priority order)

1. **CI matrix** — build+test on Linux/macOS/Windows and `wasm32`, and a Meshtastic
   loopback once a device is available. Cheap, catches the portability claims.
2. **Split `lib.rs`** into `router.rs` / `crypto.rs` / `app.rs` like `bridge/`.
3. **ESP32 crate** — the highest-value new platform; the driver makes it small.
4. **Web adapters** — WebSocket + WebRTC + Nostr ship in `web/` (loopback and a
   WebSocket relay tested); next are WebTransport and Web Serial/Bluetooth.
5. **Production hardening** — §10 quotas, chunk pinning, mix timing policy, KEYROT.

Nothing here blocks using the reference as-is; these are the road from *reference*
to *fleet*.

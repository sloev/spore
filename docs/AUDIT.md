# Project audit & review

*A review of the SPORE reference implementation: what's here, how good it is, and
what each target platform needs. Written against the code, not the intentions.*

## Verdict

The repository is a **complete, tested reference implementation of the SPORE v1
spec** (§1–§10 plus the Page-2 bindings), ~6,250 lines of Rust across a router
kernel and one file per layer, with **50 passing tests and zero warnings**
(`cargo fmt` + `clippy -D warnings` enforced in CI on Linux/macOS/Windows +
`wasm32`). It ships a C ABI with autogenerated Python/Go/JS wrappers, a browser
node (wasm + JS hub/transports) with a live demo, and a single config-driven
daemon that runs any mix of bridges. The architecture holds: one
medium-independent router, and everything else — files, sessions, crypto,
anonymity, congestion, quotas, bridges — is additive and, where it belongs,
generic. Suitable as a spec-faithful reference and a solid base for real
deployments. The remaining gap to a shipped product is per-platform packaging
(notably ESP32) and hardware-in-the-loop verification of the radio bridges.

## Code quality

<details>
<summary>Strengths, and the honest weak spots</summary>

**Strengths.** Small, layered, well-commented; the transport/router boundary is
crisp; the kernel lives in `lib.rs` and each layer (session, ratchet, mix, topic,
congestion, file, rpc, feed, kiss, armor) is its own file, mirroring `bridge/`.
Bridges share one address resolver and one datagram driver, so a new medium is a
thin `recv`/`send` shim. No `unsafe` outside the FFI. Deterministic tests cover
every layer end-to-end, and `fmt`/`clippy` are clean and CI-enforced.

**Weak spots worth knowing.**
- The Meshtastic codec is a **template**: protobuf field numbers, the multicast
  group/port, and channel encryption must be checked against real firmware (called
  out in the module). Not hardware-verified here — same for the other radio pipes
  (LoRa, AX.25, Reticulum) which have codecs/framers but no device loopback in CI.
- The reliable stream is Go-Back-N with a fixed window — correct, not tuned.
- The audio modem is tested against synthetic PCM (clean, noisy, offset); a real
  acoustic channel (echo, AGC, clock drift) will need field tuning.
- Mix mode now ships the timing policy (Poisson delays, decoys) as code, but a
  deployed anonymity network still needs a *flowing* decoy population to defeat a
  global observer — that's an operational property, not just a primitive.
</details>

## Security review

<details>
<summary>What's sound, and what to check before trusting it</summary>

- **Cryptographic identity is self-authenticating** (address = hash of the
  Ed25519 key); path learning and `Neighbors` bind only from *signed* frames, so
  an attacker can't claim someone else's address without their key. Interception
  of a directed unicast heals via flood-fallback (§5.6), and confidentiality is
  end-to-end, so it degrades to ARP-spoofing-grade nuisance, not compromise.
- **Forward secrecy** comes from prekey rotation, the Double Ratchet, and (for
  topics) KEYROT; replays are rejected (envelope dedup, ratchet skip-window,
  session replay window).
- **Flooding abuse is bounded** by per-source token-bucket quotas (§10): no single
  origin can make a node store/relay beyond a sustained byte rate, and the quota
  table itself is LRU-bounded against forged one-off sources. Stamped
  (proof-of-work) mail bypasses the quota by design.
- **`src/ffi.rs` is `unsafe` by nature** (a C ABI trusts caller pointers/lengths).
  The generated wrappers uphold the contract, but any hand-written FFI caller must
  too. This is the main surface a security pass should focus on; the wasm node ABI
  (`src/wasm.rs`) has the same contract.
- **Still to review:** constant-time behaviour of the hand-rolled Base32/Base64/
  protobuf (low risk — not key-dependent), and a global-observer defence for mix
  mode (needs the flowing decoys above).
- No unsafe deps beyond the vetted RustCrypto/dalek stack; deps are pinned.
</details>

## Portability — the platform daemon

A **single config-driven daemon** (`src/main.rs`, `cargo run -- node.yaml`) runs
any set of bridges on one shared node. Because it's plain `std` (threads +
sockets + fs), the same binary targets every desktop and mobile OS; the browser
and microcontrollers need a thin platform layer over the *same* core.

<details>
<summary>Deep dive: status per target, and what each still needs</summary>

| Target | Core | Daemon | What's needed |
|---|---|---|---|
| **Linux** | ✅ | ✅ tested + CI | — |
| **macOS** | ✅ | ✅ CI (build+test) | hardware bridges (BLE etc.) still Linux-first |
| **Windows** | ✅ | ✅ CI (build+test) | — |
| **Android** | ✅ | ✅ (std) | cross-compile with the NDK; wrap the daemon in a foreground service; add WiFi-Direct/BLE bridges |
| **Web / wasm** | ✅ | ✅ node + hub + transports | ships in `web/`: a single-import `wasm32` build (getrandom `custom`, no wasm-bindgen), a node ABI (`src/wasm.rs`), a JS `Hub`, transports (WebSocket + loopback tested in Node; WebRTC + Nostr written), and a live demo tested in headless Chromium |
| **ESP32** | ◑ | ▢ | build under `esp-idf` (which provides `std`); implement one `DatagramTransport` for ESP-NOW/Wi-Fi. The generic driver + `Neighbors` are reused unchanged |

**Web transports** are thin JS shims — a `send(bytes)`/`receive(bytes)` pair over
the browser's own API, dispatched by the JS `Hub`. Shipped: WebSocket, loopback
(both tested), WebRTC DataChannel, Nostr. Same shape, still to wrap: WebTransport
(QUIC), Web Serial/USB, Web Bluetooth, ultrasonic, QR camera. See `web/README.md`.

**The key point:** the medium-independent work — router, `Neighbors<U>`,
fragmentation, the datagram driver, quotas — is all in the portable lib. Every
remaining platform/transport is a `recv`/`send` shim, exactly as the ESP32 and
web rows above describe.
</details>

## Recommendations (priority order)

1. **ESP32 crate** — the highest-value remaining platform; build under `esp-idf`
   and add one `DatagramTransport` for ESP-NOW. The generic driver makes it small.
2. **Hardware-in-the-loop** — a Meshtastic/LoRa/AX.25 device loopback to verify
   the radio codecs against real firmware, and a real acoustic test for the modem.
3. **Finish the web transports** — WebTransport, Web Serial/Bluetooth; wire them
   into the demo.
4. **Anonymity operations** — a decoy-traffic runner using `mix::TimingPolicy` so
   mix mode resists a global observer, not just a local one.
5. **Stream tuning** — a proper congestion-controlled ARQ if SPORE-over-TCP-like
   sessions carry bulk data.

**Done since the first audit:** CI matrix + fmt/clippy gates, `lib.rs` split into
per-layer files, §10 per-source quotas, in-progress file-chunk pinning, §9 mix
timing policy (Poisson + decoys), §7 KEYROT, the browser node + transports + demo,
and the expanded bridge matrix (audio, SSB, primary-subnet broadcast, Meshtastic
serial/BLE, Reticulum, and many overlay/store-and-forward carriers).

Nothing here blocks using the reference as-is; these are the road from *reference*
to *fleet*.
